# Evidence and decisions

Keep interface, execution, task and goal validation distinct. Schema validation proves a shape; source quotations and hashes prove traceability; independent labels or expert review support domain correctness; an actual user task and acceptance support goal achievement. Record null for unknown cost and do not invent improvement percentages without a comparable baseline.

Freeze the acceptance input and rule version before the candidate run. Evidence includes artifact hashes, goal revision, candidate/acceptance fingerprints and verifier version. `verify_candidate` runs a declared verifier and stores its report separately from the worker output. Acceptance checks current evidence and current goal. If validation criteria need correction, version them and rerun both the baseline and candidate.

The registered program/service/artifact/domain verifiers inspect actual executed outputs. Architecture-linked checks enforce saved acceptance_id/config, requirements and selected intelligence profile. Launch evidence is required for independent entrypoints; live inference alone does not establish user-goal acceptance. Whole-goal coverage must include every active requirement. The materials verifier checks exported inventory, hashes, quoted text, labels and bound human decisions. Without a reference label mapping it cannot establish semantic accuracy; the report states this. Source ID keys are relative to the input directory. Human review records must remain attributable to the actual human decision; test actors are clearly labeled simulations.

Keep failed attempts, timeouts and environment errors in reports. The complete 0.2 evaluation has no dedicated Skill, generic rules, frozen alpha.4 and new Builder: six cases across three families/development+holdout, five repeats each, 120 total. The native multi-turn runner freezes host configuration and checks implicit Skill disablement; simulated users and actual human trial remain separately labeled. Use the same host, inputs, permissions and limits with at least five attempts per key condition, separated development and holdout scenarios. This minimum can reveal instability; it does not prove a population success rate. Check actual files and state, not only the final reply.

For a Skill update, add the previous-Skill condition and freeze both versions before execution. The source repository and separate `*-development.zip` provide `tools/evaluate.py` with `--baseline-skill`, measured wall time, artifact hashes and paired summaries; read `evals/README.md` there. The installable plugin ZIP, standalone Skill ZIP and wheel do not contain evaluation drivers or corpus. Use a source checkout/development bundle for evaluation; inspect the resource before choosing its actual path, without initializing a target or installing tools just to answer a verification question. Keep unknown cost, tokens and model calls null, and assess human rubric items separately. Clean host sessions must prevent implicit Skill loading in the no-Skill baseline; the driver cannot attest host isolation.
